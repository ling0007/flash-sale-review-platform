# 黑马点评限流改造：从“套算法”到按场景选型的工程权衡

> 项目背景：黑马点评秒杀链路已完成 Redis Lua 预扣 + RabbitMQ 异步下单等改造。下一条主线不是继续堆“缓存三件套”，而是补真正的入口限流与接口防刷。
>
> 最终方案：
>
> - 秒杀 USER：Sliding Window Counter（滑动窗口计数器）
> - 秒杀 GLOBAL：Token Bucket（令牌桶）
> - 验证码：`SET NX EX`
> - 普通接口 IP：Sliding Window Counter
>
> 实现原则：限流发生在订单 ID、`seckill.lua` 和 RabbitMQ 之前；限流与库存预扣、MQ 消费、数据库事务保持解耦。

---

## 1. 为什么要给黑马点评补限流

原始秒杀链路已经能够处理：

```text
HTTP 请求
  ↓
Controller
  ↓
VoucherOrderServiceImpl
  ↓
seckill.lua
  ├─ 检查 Redis 库存
  ├─ 检查一人一单
  ├─ 预扣 Redis 库存
  └─ 记录购买资格
  ↓
RabbitMQ
  ↓
消费者
  ↓
Redisson 用户锁
  ↓
MySQL 条件扣库存 + 插入订单
```

RabbitMQ 解决的是**后端处理速度与流量峰值之间的矛盾**，但它并不能阻止大量无意义请求先进入秒杀入口。

例如：

- 单个用户使用脚本每秒请求几百次；
- 秒杀开始瞬间，大量用户同时冲击 Redis；
- 大量请求虽然最终会因为库存不足或一人一单失败，但仍然执行了 ID 生成、Redis Lua、日志和 MQ 前置逻辑；
- 验证码接口被连续调用时会不断覆盖旧验证码，未来接入真实短信服务后还会产生外部成本。

因此需要在业务链路最前面增加一层流量治理：

```text
请求
  ↓
限流
  ↓
通过后才进入真正业务
  ↓
seckill.lua
  ↓
RabbitMQ
```

这里的目标不是“保证公平抢购”，而是**保护系统容量、降低恶意/重复请求的成本，并尽早拒绝无意义流量**。

---

# 2. 最初方案：固定窗口

第一版设计是：

```text
@RateLimit
  ↓
Spring AOP
  ↓
Redis Lua
  ↓
GET / INCR / PEXPIRE
```

例如用户限流：

```text
rate_limit:seckill:user:42
value = 3
TTL = 1s
```

Lua 原子完成：

1. 读取当前次数；
2. 判断是否超过阈值；
3. `INCR`；
4. 首次请求设置 TTL。

### 优点

- 实现简单；
- 每个 bucket 只保存一个整数，空间 O(1)；
- Redis 开销低；
- 非常容易通过 Lua 保证原子性。

### 问题：窗口边界突刺

假设限制：

```text
1 秒最多 100 次
```

固定窗口可能出现：

```text
第 0.9 ~ 1.0 秒：100 次
第 1.0 ~ 1.1 秒：100 次
```

在真实的 0.2 秒时间范围内，系统实际承受了 200 次请求。

因此固定窗口非常轻量，但对秒杀这种明显具有瞬时洪峰的入口来说，流量平滑能力不足。

---

# 3. 第二版方案：ZSET Sliding Window Log

之后考虑参考常见的：

```text
自定义注解
  ↓
AOP
  ↓
Redis ZSET
  ↓
Lua
```

每一个放行请求都保存一个时间戳：

```text
ZSET

score = 请求时间戳
member = 唯一请求 ID
```

Lua 每次执行：

```text
ZREMRANGEBYSCORE
  ↓
删除窗口外记录
  ↓
ZCARD
  ↓
统计最近窗口请求数
  ↓
达到 limit？
  ├─ 是：拒绝
  └─ 否：ZADD 当前请求
```

这样可以得到严格的：

```text
(now - window, now]
```

最近窗口统计。

### 它解决了什么

相比固定窗口，它没有明显的整点边界问题。

例如“最近 1 秒最多 100 次”，就是严格统计最近 1 秒，而不是把时间粗暴切成：

```text
12:00:00 ~ 12:00:01
12:00:01 ~ 12:00:02
```

### 但进一步学习后发现：它未必适合秒杀 GLOBAL

Sliding Window Log 的代价是：

> 每一个有效请求都需要成为 ZSET 中的一条 member。

如果：

```text
GLOBAL limit = 5000 req/s
window = 1s
```

则一个 GLOBAL ZSET 中可能长期维护数千条 member。

如果窗口扩大：

```text
10 秒最多 50000 次
```

则可能维护数万条。

其空间复杂度从固定窗口的：

```text
O(1)
```

变成：

```text
O(N)
```

其中 N 为窗口内成功请求数。

同时还需要：

```text
ZREMRANGEBYSCORE
ZCARD
ZADD
PEXPIRE
```

ZSET 本身也比整数计数器更重。

这时候需要重新问一个问题：

> 秒杀限流真的需要知道“最近一秒具体有哪些请求”吗？

答案通常是否定的。

秒杀 GLOBAL 限流本质是**容量保护阀**，并不负责决定谁最终买到商品。

后面仍然有：

```text
seckill.lua
库存判断
一人一单
RabbitMQ
数据库约束
```

因此秒杀入口更关心：

```text
吞吐
低开销
流量整形
系统可承受范围
```

而不是逐请求时间戳级别的绝对精确。

---

# 4. Sliding Window Log 和 Counter 的真正区别

## 4.1 Sliding Window Log

核心问题：

> 最近 N 秒**准确发生了哪些请求**？

典型实现：

```text
Redis ZSET
score = timestamp
member = requestId
```

特点：

- 精确；
- 每个请求都留记录；
- 空间 O(N)；
- 更适合阈值不高、对精确时间窗口敏感的场景。

例如：

- 登录失败风控；
- 安全敏感接口；
- 某些需要严格统计最近 N 分钟行为次数的场景。

但限流 ZSET 不应该被当成正式审计系统。真正支付、风控、安全审计仍应进入持久化日志或专门系统。

---

## 4.2 Sliding Window Counter

核心问题：

> 最近 N 秒**大约发生了多少请求**？

它不保存每一次请求，而是保存相邻时间桶的计数。

例如：

```text
上一窗口：100
当前窗口：40

当前窗口已经过去 30%
```

近似计算：

```text
estimated =
previousCount × (1 - 0.3)
+ currentCount

= 100 × 0.7 + 40
= 110
```

特点：

- 每个 bucket 状态量固定，空间近似 O(1)；
- 没有 ZSET 逐请求 member；
- 比固定窗口平滑；
- 存在少量估算误差；
- 非常适合作为普通 API / 用户接口防刷。

对秒杀 USER 来说：

```text
用户 42 对券 7
最近 1 秒大约不能超过 5 次
```

这种语义完全够用。

即使真实最近一秒是 6 次、估算值出现轻微偏差，也不会影响库存正确性，因为最终库存与一人一单仍由秒杀 Lua 和数据库兜底。

---

# 5. 为什么秒杀 GLOBAL 最终选择 Token Bucket

秒杀的流量并不是均匀到来的。

真实形态更像：

```text
开抢瞬间：
██████████████████████████

随后：
████████
████
██
```

它天然具有 burst（突发流量）。

如果使用：

```text
Sliding Window
limit = 1000 req/s
```

语义更接近：

> 最近一秒已经达到 1000 次，就拒绝新的请求。

但真实系统往往具有一定的瞬时余量。

例如：

```text
长期稳定处理能力：1000 req/s
短时间可以承受：1500 req
```

这时 Token Bucket 更贴近系统容量模型。

---

## 5.1 Token Bucket 的两个核心参数

```text
refillRate
capacity
```

例如：

```text
refillRate = 1000 tokens/s
capacity = 1500 tokens
```

含义：

- 长期平均允许速率约为 1000 req/s；
- 桶中最多积累 1500 token；
- 系统空闲后可以积累 token；
- 秒杀开始瞬间允许一定 burst；
- token 用完后，新的请求只能随着 token 按 1000/s 的速度补充而进入。

这实现的是：

```text
长期平均速率
+
可控突发
```

而不是死板的“任意 1 秒绝对不能超过 X”。

---

## 5.2 Token Bucket 的核心计算

桶保存：

```text
tokens
lastRefillTime
```

请求进入后：

```text
elapsed = now - lastRefillTime

tokens =
min(
    capacity,
    oldTokens + elapsed × refillRate
)
```

然后：

```text
tokens >= 1
  → tokens -= 1
  → allow

tokens < 1
  → reject
```

Redis + Lua 可以保证：

```text
读取状态
→ 计算补充
→ 判断
→ 扣 token
→ 更新时间
```

原子执行。

# 6. 最终方案：按场景选择算法，而不是强行统一

最终决定：

| 业务 | 算法 | 原因 |
|---|---|---|
| 秒杀 USER | Sliding Window Counter | 防止单用户短时间疯狂刷同一张券 |
| 秒杀 GLOBAL | Token Bucket | 秒杀天然 burst，需要控制平均速率同时允许一定瞬时余量 |
| 验证码 | `SET NX EX` | 本质就是手机号 60 秒冷却，不需要复杂算法 |
| 普通接口 IP | Sliding Window Counter | 低内存、通用，适合接口防刷 |
| 登录失败/安全风控（未来） | Sliding Window Log | 只有需要严格最近窗口统计时才值得使用 |

核心原则：

> 算法服务业务语义，而不是为了统一框架让业务迁就算法。

# 8. 为什么选择“路线 A”：两个限流器分开调用

这里有一个值得主动讲的工程 trade-off。

理论上最严格的做法是：

```text
USER Counter 判断
+
GLOBAL Token Bucket 判断
+
全部通过
+
USER +1
+
GLOBAL token -1
```

全部放进同一个 Lua。

这样能得到：

```text
两边都通过才同时消费额度
```

但代价是：

- Lua 同时包含两种算法；
- 通用限流器变成秒杀专用混合脚本；
- 开发、测试、维护复杂度提高；
- 后续每增加一种算法，组合爆炸。

因此本项目选择路线 A：

```text
GLOBAL Token Bucket
        ↓
USER Sliding Window Counter
        ↓
原有秒杀业务
```

或者根据最终实现约定固定一个顺序。

### 接受的代价

可能出现：

```text
GLOBAL 已消费一个 token
        ↓
USER 随后被限流
```

于是一个 GLOBAL token 被浪费。

或者反过来，如果先 USER：

```text
USER 已记录一次
        ↓
GLOBAL 随后拒绝
```

导致 USER 配额被轻微消耗。

### 为什么可以接受

限流额度不是库存、余额或订单状态，它属于流量治理的近似控制状态。

这里不值得为了少量配额损耗引入：

```text
跨算法补偿
回滚 Lua
复杂混合脚本
```

项目选择：

> 接受极少量限流配额损耗，以换取算法模块清晰、实现简单、可测试和可维护。

真正不能接受的不一致仍然由：

```text
seckill.lua
RabbitMQ 幂等
MySQL 库存条件更新
唯一约束
```

等业务链路负责。

这也是“强一致应该用在哪里”的工程判断。

# 9. 验证码为什么不用统一限流框架硬套

验证码业务规则是：

```text
同手机号 60 秒只能发送一次
```

最自然的 Redis 表达：

```redis
SET sms:cooldown:{phone} 1 NX EX 60
```

返回成功：

```text
允许发送
```

NX 失败：

```text
60 秒冷却期未结束
→ 拒绝
```

如果硬套 Token Bucket：

```text
capacity = 1
refill = 1 / 60s
```

数学上没错，但复杂度完全没有必要。

如果硬套 Sliding Window Counter：

```text
60 秒 limit = 1
```

也能实现，但语义没有 `SET NX EX` 直接。

因此验证码不为了“技术统一”牺牲简单性。

同时应该：

```text
先校验手机号格式
↓
再 SET NX EX
↓
再生成验证码
↓
保存验证码
↓
发送
```

避免非法手机号制造无意义 Redis key。

# 10. 普通接口 IP 限流

对于查询类、普通业务接口：

```text
某 IP
最近 10 秒
大约最多 100 次
```

使用 Sliding Window Counter 即可。

Key 可设计为：

```text
rate_limit:api:{resource}:ip:{ip}
```

注意真实 IP 获取：

- 直连使用 `request.getRemoteAddr()`；
- 如果经过 Nginx，应由可信代理设置 `X-Real-IP` / `X-Forwarded-For`；
- 后端只有在来源属于可信代理时才相信这些 header；
- 不能直接信任客户端自己传入的 `X-Forwarded-For`，否则 IP 限流可被绕过。

# 11. 为什么限流必须在 seckill.lua 和 MQ 之前

错误顺序：

```text
请求
↓
订单 ID
↓
seckill.lua
↓
RabbitMQ
↓
限流
```

此时系统资源已经被消耗。

正确顺序：

```text
请求
↓
限流
↓
订单 ID
↓
seckill.lua
↓
RabbitMQ
```

这样被拒绝的请求：

- 不生成订单 ID；
- 不执行库存 Lua；
- 不预扣库存；
- 不记录购买资格；
- 不向 MQ 发消息；
- 不进入数据库链路。

限流的价值就是：

> 尽可能早地丢弃不值得处理的请求。

# 12. Redis 故障时为什么选择 fail-closed

两种常见策略：

```text
fail-open
限流服务失败 → 放行业务
```

```text
fail-closed
限流服务失败 → 拒绝业务
```

秒杀最终选择偏向 fail-closed。

原因：

1. 秒杀本来就强依赖 Redis；
2. Redis 不可用时，后续 `seckill.lua` 本身也无法正常工作；
3. 在限流 Redis 异常时继续放行，并不能真正提高秒杀可用性；
4. 反而可能让故障期间的洪峰继续冲击其他资源。

验证码也更倾向 fail-closed：

- 未来短信存在真实成本；
- Redis 异常时无限放行验证码发送风险更高。

HTTP 语义建议区分：

```text
429 Too Many Requests
→ 正常触发限流

503 Service Unavailable
→ 限流基础设施 / Redis 异常
```

正常限流不应该打印完整 ERROR 堆栈；真正基础设施异常才记录 ERROR。

# 13. 这个方案比“装 Sentinel”好在哪里

项目目标不是：

> 简历里出现 Sentinel、令牌桶、滑动窗口几个关键词。

而是可以回答：

```text
为什么这里需要限流？
为什么 USER 和 GLOBAL 用不同算法？
为什么不用 Sliding Window Log？
为什么验证码不用统一注解？
为什么允许两级限流存在少量配额损耗？
为什么限流在 MQ 前？
Redis 挂了怎么办？
```

整个故事是一条完整的工程决策链：

```text
发现秒杀入口存在流量攻击面
↓
最初考虑固定窗口
↓
发现固定窗口边界突刺
↓
评估 ZSET Sliding Window Log
↓
发现逐请求记录带来 O(N) 内存与 ZSET 成本
↓
区分“用户防刷”和“全局容量保护”的不同业务语义
↓
USER 选择 Sliding Window Counter
↓
GLOBAL 选择 Token Bucket
↓
验证码回归 SET NX EX
↓
保留 Redis + Lua 原子性
↓
AOP 做声明式接入
↓
在 seckill.lua / MQ 前完成入口流量治理
↓
最后通过压测确定真实阈值
```

这比“照一篇博客实现 ZSET 限流”更值得在面试展开。

# 14. 面试高频问答

## Q1：为什么秒杀要做两级限流？

USER 和 GLOBAL 解决的问题不同。

USER：

> 防止单个用户脚本不断重复请求同一张券，降低无意义请求。

GLOBAL：

> 防止大量不同用户同时把整个秒杀入口、Redis、线程池和 MQ 前置链路打满。

只做 USER 无法应对大量不同账号；只做 GLOBAL 又不能针对恶意用户单独约束。

---

## Q2：为什么 USER 用 Sliding Window Counter？

用户防刷关注的是：

> 最近一小段时间内请求次数是否过多。

不需要保存每一次请求时间戳。

Sliding Window Counter 相比固定窗口减轻边界突刺，又比 ZSET Sliding Window Log 内存更低，单 bucket 状态量近似 O(1)，适合大量用户 key。

---

## Q3：为什么 GLOBAL 用 Token Bucket？

秒杀流量天然具有 burst。

GLOBAL 的目标不是严格统计“最近 1 秒精确有多少请求”，而是保护系统整体吞吐。

Token Bucket 可以：

- 用 refill rate 控制长期平均流量；
- 用 capacity 允许系统承受范围内的瞬时 burst。

它比死板的窗口阈值更贴近秒杀入口的实际容量模型。

---

## Q4：为什么不用 ZSET Sliding Window Log？

它是精确算法，但每个放行请求都需要一个 ZSET member。

对于高 QPS GLOBAL 限流：

```text
空间复杂度 O(N)
```

还存在 ZSET 插入、清理和 member 字符串开销。

秒杀限流只是容量保护，不需要逐请求时间戳精度，因此使用 Log 的成本收益比不高。

---

## Q5：Sliding Window Counter 不精确，会不会超卖？

不会。

限流不是库存正确性机制。

库存正确性仍然由：

```text
seckill.lua
Redis 库存
一人一单
MySQL 条件扣库存
数据库约束
```

保证。

Counter 的小误差只影响少量请求是提前/延后被限流，不会直接导致超卖。

---

## Q6：为什么不用 Token Bucket 统一所有接口？

算法应该匹配业务语义。

验证码：

```text
60 秒只能一次
```

直接 `SET NX EX` 最自然。

USER 防刷：

```text
最近 N 秒大约最多 M 次
```

Sliding Window Counter 更直观。

GLOBAL：

```text
控制平均流量，但允许 burst
```

Token Bucket 更合适。

强行统一算法只会增加理解和维护成本。

---

## Q7：为什么 USER + GLOBAL 不放在一个 Lua 里？

如果使用相同算法，放在一个 Lua 中可以做到“全部通过才一起消费额度”。

但最终 USER 和 GLOBAL 使用了不同算法：

```text
Sliding Window Counter
+
Token Bucket
```

如果为了绝对原子而写一个混合 Lua，会让通用限流器变成秒杀专用脚本。

项目选择分开执行，接受极少量配额浪费，以换取模块清晰和可维护性。

限流配额不是订单、库存、余额这类必须强一致的业务状态，因此这个 trade-off 可以接受。

---

## Q8：如果 GLOBAL 先扣 token，USER 随后失败怎么办？

这个 token 会被浪费。

项目明确接受这种情况。

原因是：

- 只影响很小的流量额度；
- token 后续会自动补充；
- 不影响业务数据正确性；
- 为它增加补偿机制得不偿失。

这是有意识的最终一致/近似治理取舍，而不是遗漏。

---

## Q9：两级限流调用顺序怎么选？

可以固定：

```text
GLOBAL Token Bucket
↓
USER Sliding Window Counter
```

这样系统已经全局过载时，可以尽早拒绝，避免创建大量 USER key 或进行额外用户级计算。

也可以基于压测调整。

重点不是绝对唯一顺序，而是：

- 顺序固定；
- 行为有测试；
- 能解释可能存在的配额浪费。

---

## Q10：为什么使用 Redis + Lua？

因为服务未来可能多实例部署。

如果使用 JVM 内存计数：

```text
实例 A：50
实例 B：50
```

每台机器只看到自己的流量，无法得到全局限制。

Redis 提供共享状态。

Lua 可以把：

```text
读取状态
计算
判断
修改
设置 TTL
```

作为一次原子脚本执行，避免多个 Redis 命令之间的并发竞态。

---

## Q11：为什么不用 Redisson RateLimiter？

Redisson 的现成限流组件当然能解决部分问题。

本项目自己实现的原因是：

- 希望明确掌握算法和 Redis 状态模型；
- USER Counter 与 GLOBAL Token Bucket 的语义不同；
- 需要结合项目自己的注解、key 和异常体系；
- 简历项目更希望能解释底层，而不是只会调用 API。

真实生产环境如果已有成熟网关 / Sentinel / Redisson 方案，应根据团队基础设施选择，不代表必须手写。

---

## Q12：为什么限流放在 Controller AOP，而不是 Service？

限流属于 HTTP 入口流量治理。

放在 Controller 方法执行前，可以确保：

```text
订单 ID
Redis 库存 Lua
RabbitMQ
```

全部还没发生。

并且 Controller 没有同类自调用导致 AOP 失效的问题。

---

## Q13：AOP 有什么坑？

主要注意：

1. Spring AOP 依赖代理，同类内部自调用不会经过代理；
2. 重复注解要确认 Aspect 能取到全部规则；
3. 用户维度依赖 `UserHolder` 时，要保证登录拦截器先执行；
4. IP 维度不能盲目信任客户端 `X-Forwarded-For`；
5. 不能把复杂业务逻辑塞进 Aspect。

---

## Q14：Redis 挂了怎么办？

秒杀采用 fail-closed。

因为后面的秒杀库存判断本身也依赖 Redis。

返回：

```text
503 Service Unavailable
```

而正常达到限流阈值：

```text
429 Too Many Requests
```

两者不能混为“服务器异常”。

---

## Q15：限流阈值怎么定？

不能拍脑袋写：

```text
GLOBAL = 1000/s
```

应该通过压测确定：

- 应用线程池；
- Redis Lua 延迟；
- Redis CPU；
- MQ 入队速率；
- 消费速度；
- DB 最终吞吐；
- P95 / P99 延迟。

Token Bucket：

```text
refillRate
```

接近系统希望长期稳定承受的入口速率。

```text
capacity
```

则根据短时间 burst 承受能力设置。

---

## Q16：RabbitMQ 已经削峰了，为什么还需要限流？

MQ 解决的是：

> 已经被系统接受的任务如何异步处理。

限流解决的是：

> 哪些请求根本不应该进入系统。

如果所有流量都先进 Redis、生成订单 ID、执行 Lua，再发 MQ，入口依旧可能被打垮。

二者职责不同：

```text
限流 → 入口保护
MQ   → 后端削峰
```

---

## Q17：限流和 seckill.lua 为什么不能合并？

两者职责不同。

限流：

```text
流量治理
```

seckill.lua：

```text
库存 + 一人一单 + 购买资格
```

合并会让 Lua 变成巨型脚本：

- 难测试；
- 难复用；
- 难调整算法；
- 流量策略变化会影响核心秒杀业务。

因此保持两个独立模块。

---

# 15. 后续压测计划

代码完成后至少验证四组场景。

## 场景 1：USER Counter

例如：

```text
用户限制：5 req/s
```

同一个用户连续发送：

```text
100 req/s
```

观察：

- 大部分返回 429；
- 少量请求进入业务；
- 不同用户互不干扰。

---

## 场景 2：GLOBAL Token Bucket

例如：

```text
refillRate = 1000/s
capacity = 1500
```

制造明显 burst。

验证：

- 初始可以接受一定突发；
- token 耗尽后，放行速率逐渐受 refillRate 控制；
- Redis / MQ 峰值低于无限制情况。

---

## 场景 3：验证码

连续请求同一手机号：

```text
第一次成功
60 秒内后续失败
```

不同手机号互不影响。

---

## 场景 4：限流前后系统对比

关注：

```text
接口 QPS
429 数量
Redis CPU
Lua P95/P99
RabbitMQ 入队量
消费者积压
数据库订单写入量
```

不要把目标写成“加入限流后 QPS 更高”。

正确目标是：

> 在洪峰情况下，把系统内部负载控制在可接受范围，同时快速拒绝多余流量。

# 17. 项目故事的一句话版本

> 我最初准备照常见博客用 Redis ZSET 做滑动窗口限流，但进一步分析后发现 Sliding Window Log 会为每个请求保存 member，高 QPS 秒杀 GLOBAL 场景成本偏高；因此没有为了“统一技术栈”硬套一种算法，而是根据业务语义重新选型：USER 防刷用 O(1) 状态的 Sliding Window Counter，GLOBAL 用能够允许可控 burst 的 Token Bucket，验证码直接用 SET NX EX。最终限流只负责入口流量治理，库存正确性继续由原有 seckill.lua、RabbitMQ 和数据库链路负责。

这就是这次改造最值得在面试讲的部分。
